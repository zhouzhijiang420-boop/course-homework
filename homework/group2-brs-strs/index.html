PART 01

业务需求规格说明 BRS（表 4-1）

1.简介

1.1 业务目的

高级别自动驾驶（L4/L5）逐步从示范运营走向城市载客、高速干线物流与末端配送的商业化落地。传统底盘依赖方向盘、踏板与驾驶员机械操作，无法满足无人化、高冗余、毫秒级执行的要求。本项目旨在建设一套平台化、可复用、可通过功能安全认证的线控底盘平台：接收自动驾驶大脑下发的规划轨迹，无机械连接地完成转向、制动、驱动与悬架控制，使整车厂与自动驾驶运营商无需针对每一车型重复开发底盘执行系统，从而缩短量产周期、降低安全认证成本，并支撑载客与物流场景的商业闭环。

1.2 业务范围

  • 业务域：智能网联汽车底盘电控与线控执行系统的平台化需求定义与产品交付。
  • 纳入范围：线控转向（SbW）、线控制动（BBW）、线控驱动（DbW）、主动悬架、底盘域控制器、冗余安全系统的业务与运行需求；接口定义、运行模式与质量目标。
  • 排除范围：自动驾驶感知、决策与规划算法（属于上游智驾系统）；整车车身结构、内外饰造型；动力电池本体研发。
  • 外部实体：自动驾驶大脑（规控系统）、整车厂（OEM）、Robotaxi / 物流运营商、远程安全员、底盘零部件供应商、监管与认证机构、售后维保体系。

1.3 业务概况

平台在整车体系中处于「决策」与「车轮」之间的执行层：上游接入自动驾驶大脑、高精定位与 V2X 车路协同信息；中游由底盘域控制器统一解算并协调四大执行系统与冗余安全单元；下游面向整车集成、车队运营与售后维保。业务链条为：需求定义 → 平台开发 → 车型适配 → 测试认证 → 整车集成 → 运营投放 → 监控运维 → 迭代升级。

1.4 定义

本说明中的核心术语见 8.1 缩写与缩略语；六层系统结构（任务—体系—整机—系统—子系统—模块）沿用小组作业 1 的拆解结论。

1.5 主要相关方

主要相关方包括：自动驾驶系统开发商、整车厂、车队运营商、乘客、远程安全员、底盘与零部件供应商、监管/认证机构、售后维保团队及平台研发团队。各方的诉求与对系统的影响详见 StRS 1.5 相关方列表。

3.业务管理需求

3.1 业务环境

  • 政策法规：自动驾驶准入与上路试点政策、数据安全要求、车规级功能安全与信息安全法规逐步完善。
  • 市场趋势：Robotaxi 城市载客、高速干线物流、无人配送与自动代客泊车等场景进入规模化示范阶段。
  • 技术基础：车规芯片、双冗余执行器、以太网/CAN FD 通信与电控悬架技术日趋成熟，支撑线控平台落地。
  • 社会责任：载客场景对安全、平顺与事故责任界定的社会预期显著高于普通商用车辆。

3.2 使命、目的与目标

使命：为高级别自动驾驶提供安全、实时、可冗余的底盘执行底座，把驾驶意图毫秒级、无机械连接地翻译成车轮运动。

  • 平台可适配至少两类整车（乘用车 / 商用车），降低重复开发成本；
  • 控制指令响应延迟 ≤ 20ms，转向轨迹跟踪精度 ±0.1°；
  • 关键执行与链路达到 ASIL-D 相关要求，单点失效仍可安全停车；
  • 支持在线监测、远程诊断与 OTA 升级及回滚。

3.3 业务模型

平台以「平台化底座 + 车型适配开发」方式交付：底盘平台本体在多车型间复用，针对具体整车做布置、接口与标定适配；通过零部件配套、平台授权与联合交付智驾整车方案获取收益。上游与智驾方案商协同定义接口，下游面向 OEM 与运营商提供产品、标定与维保支持。

3.4 信息环境

  • 项目组合：底盘平台与整车电子电气架构、智驾平台项目统一规划优先级与接口约束。
  • 长期系统计划：遵循由分布式电控向集中式底盘域控演进的架构路线，预留算力与接口扩展空间。
  • 数据配置：统一管理车辆运行数据、故障日志、标定参数与 OTA 版本，保证可追溯、可回滚。

4.业务运行需求

4.1 业务过程

业务流程按层次分解，每一过程有唯一名称与编号：

  • BP-01 需求定义：收集业务与相关方需求，冻结平台规格与接口基线。
  • BP-02 平台开发：子系统开发、集成与台架验证。
  • BP-03 车型适配：针对具体整车完成布置、标定与适配开发。
  • BP-04 测试认证：功能安全、性能、可靠性与法规认证测试。
  • BP-05 整车集成：与智驾系统、整车网络联调，交付整车产品。
  • BP-06 运营投放：车辆进入示范或商业运营，平台随车队运行。
  • BP-07 监控运维：在线监测、故障诊断、保养与备件更换。
  • BP-08 迭代升级：基于运行数据复盘，完成标定与软件 OTA 升级。

4.2 业务运营策略与规则

  • 规则 BR-01 安全优先：任何性能、成本与进度让步不得突破功能安全底线。
  • 规则 BR-02 失效降级：检测到故障后按预设策略降级运行或进入最小风险状态。
  • 规则 BR-03 配置管理：需求、接口、标定与软件版本变更必须走评审、留痕与可追溯流程。
  • 规则 BR-04 数据可追溯：运行与故障数据完整记录，支持事后复盘与责任界定。

4.3 业务运行约束

  • 必须满足道路车辆法规准入与功能安全认证要求；
  • 零部件需满足车规级温度、振动、寿命与可靠性环境条件；
  • 受整车布置、整备质量、成本与供应链可得性约束；
  • 冗余设计带来的成本、重量与功耗上升需在平台级权衡。

4.4 业务运行质量

  • 可用性：运营期间平台高可用运行，关键故障可被及时识别；
  • 效能：准确跟踪规划轨迹，转向、制动与驱动控制满足精度要求；
  • 效率：兼顾能耗与制动能量回收，降低运营成本；
  • 满意度：加减速与转向平顺，保证乘坐舒适性；
  • 使用风险：通过冗余与降级策略避免失控、误动作等使用风险。

4.5 业务结构

与平台相关的业务结构包括：平台研发团队（系统、软硬件、标定）、车型项目组、测试与认证团队、运营支持与售后维保团队；各角色职责在平台需求基线与项目流程中明确划分，并随车型项目与组织调整保持可关联、可变更。

5.提案系统初步运行概念

5.1 初步运行概念

  • 运营政策与约束：平台仅作为执行层，不承担感知决策职责；运行须在认证范围与法规允许的场景、区域内。
  • 系统描述：由底盘域控制器协调 SbW、BBW、DbW、主动悬架与冗余安全单元，接收上游轨迹与车辆状态反馈，闭环控制车轮运动。
  • 系统运行模式：正常模式、降级模式、最小风险策略（MRC）模式、驻车模式。
  • 用户类型：自动驾驶系统（主要指令方）、远程安全员（监控与接管配合）、维保人员（诊断与检修）；乘客为间接使用者。
  • 支持环境：车规级硬件、车载网络（以太网 / CAN FD）、诊断工具、云端监控与 OTA 后台。

5.2 初步运行场景

  • 场景 B-S1 城市载客：车辆在公开道路按规划轨迹跟车、变道、避让与停车，平台平顺执行转向与加减速。
  • 场景 B-S2 高速巡航：干线物流车辆高速巡航、编队行驶，平台维持车道保持与稳定制动。
  • 场景 B-S3 自动泊车：低速高精度转向与驻车制动，完成代客泊车。
  • 场景 B-S4 失效处置：单点故障触发冗余接管，降级行驶或靠边停车并告警。

6.其他初步生存周期概念

采办：平台及子系统按车规零部件流程采购或联合开发；部署：随整车集成下线，完成标定校验与自检后投放；支持：运营期提供远程监控、诊断、保养与备件支持；弃置：车辆退役时对高压部件与电控单元进行拆解、回收与数据清除。各阶段的详细概念见 StRS 第 6 章。

7.项目约束

  • 成本：平台与冗余配置需控制在整车成本目标内；
  • 进度：需求基线、车型适配、测试认证与投放节点按项目计划锁定；
  • 资源：研发算力、台架、测试场地与供应链产能构成约束条件。

3.业务管理需求

本章与 BRS 第 3 章一致，从相关方视角归纳如下：

3.1 业务环境

自动驾驶法规、商业化场景、车规技术成熟度与社会安全预期共同构成平台的外部环境（见 BRS 3.1）。

3.2 使命、目的与目标

以安全、实时、可冗余的底盘执行底座支撑高级别自动驾驶商业化（见 BRS 3.2）。

3.3 业务模型

平台化底座 + 车型适配，配套零部件与联合交付（见 BRS 3.3）。

3.4 信息环境

统一项目组合、架构演进规划与运行/故障/版本数据管理（见 BRS 3.4）。

4.系统运行需求

4.1 系统过程

  • SP-01 指令接收：接收上游规划轨迹、目标车速/转角/扭矩及车辆状态反馈。
  • SP-02 决策解算：底盘域控基于车辆动力学模型解算各执行器目标量。
  • SP-03 协同执行：协调转向、制动、驱动、悬架执行，并进行稳定性控制。
  • SP-04 状态监控：实时监测传感器、执行器、电源与通信状态，进行故障诊断。
  • SP-05 降级与告警：按故障等级触发冗余切换、降级运行或 MRC，并向运营端上报。

4.2 系统运行策略与规则

  • 控制闭环优先保证安全，其次兼顾平顺性与能耗；
  • 故障诊断覆盖传感器、执行器、电源、通信与计算链路；
  • 冗余单元在主链路失效后无缝或短时切换；
  • 所有运行与故障事件写入可追溯日志。

4.3 系统运行约束

  • 工作温度、振动、电压等满足车规环境条件；
  • 接口、信号与时序遵循整车电子电气架构规范；
  • 性能指标受整车动力、电池与传感器配置约束。

4.4 系统运行模式与状态

运行模式触发条件系统行为
正常模式自检通过、各链路无故障全功能闭环执行，跟踪规划轨迹。
降级模式出现非关键故障或冗余切换限制车速/功能范围，维持可控行驶并上报。
最小风险策略 MRC关键链路失效、无法继续安全行驶自主靠边减速停车，开启警示，等待远程介入。
驻车模式到达目的地、泊车完成或运营结束施加驻车制动，关闭动态执行，进入低功耗待命。

6.1运行概念 · 运营概念 ConOps

ConOps（运营概念）从业务与运营视角描述：平台在整个自动驾驶运营体系中被谁、在什么场景下、以什么方式使用，各方如何分工协作，以及服务水平与运营约束。

运营背景与定位

高级别自动驾驶车辆在城市道路、高速干线、园区与停车场等区域商业化运营。线控底盘平台是整车的「手脚」：不做环境感知与行驶决策，只负责把智驾大脑的规划结果安全、平顺地执行到车轮上，是运营体系中不可替代的执行底座。

相关方分工

  • 智驾系统：负责感知、决策与轨迹规划，向底盘下发运动指令；
  • 底盘平台：负责指令解算、协同执行、状态监控与失效降级；
  • 车队运营商：负责车辆调度、班次安排与运营监控；
  • 远程安全员：在监控中心观察车队状态，处置告警并配合接管；
  • 维保团队：负责出车前检查、定期保养、故障件更换与回场检修；
  • 乘客 / 货主：作为服务接受方，获得安全、舒适、准点的运输服务。

运营流程

  • 出车自检：车辆上线前完成底盘各子系统自检与状态确认；
  • 正常运营：车辆按调度在服务区域内自主行驶，平台实时执行指令；
  • 实时监控：运营端持续查看车辆状态与故障告警，远程安全员待命；
  • 异常处置：出现故障时按降级 / MRC 策略处置，必要时远程介入；
  • 回场维护：车辆回场后读取诊断数据，完成保养或备件更换；
  • 复盘迭代：汇总运行与故障数据，优化标定并通过 OTA 升级。

运营约束与服务水平

  • 运营须限定在法规允许、平台认证覆盖的场景与区域内；
  • 安全为不可突破的底线，性能与效率目标在安全前提下优化；
  • 服务水平：控制响应 ≤ 20ms、关键链路冗余、故障可远程感知与追溯。

6.2运行概念 · 运行场景 OpsCon

OpsCon（运行概念）面向具体使用环境，描述操作者 / 系统在典型场景下如何与平台交互：前置条件、系统行为、相关方交互、预期结果与异常分支。

场景 O-1 城市道路正常载客行驶

NORMAL OPERATION · URBAN
前置条件
车辆自检通过，处于正常模式，智驾大脑已下发规划轨迹与目标车速。
系统行为
底盘域控解算目标转角、扭矩与制动力，协调 SbW、DbW、BBW 与主动悬架协同执行，平顺跟踪轨迹。
相关方交互
智驾系统持续更新轨迹；平台回传车辆状态；乘客感受平顺加减速与转向。
预期结果
车辆按轨迹安全、舒适地完成跟车、变道、避让与停车。
异常分支
前方出现障碍物或突发状况时，平台按指令平稳制动；若执行链路异常，转入降级或 MRC。

场景 O-2 高速干线物流巡航

NORMAL OPERATION · HIGHWAY
前置条件
车辆进入高速巡航路段，编队或单车行驶，路况良好。
系统行为
维持车道保持与车速稳定，驱动侧进行扭矩矢量分配与能量回收，制动侧保持双回路冗余待命。
相关方交互
运营商监控车队位置与状态；远程安全员关注异常告警。
预期结果
长距离巡航稳定、低能耗，制动与转向随时可响应。
异常分支
遇编队调整、坡道或恶劣路面时，平台自动调整扭矩与阻尼；关键故障触发减速靠边。

场景 O-3 自动代客泊车（AVP）

LOW-SPEED OPERATION · PARKING
前置条件
车辆进入停车场，高精定位与环境识别完成，泊车路径规划就绪。
系统行为
低速下高精度转向，配合低速驱动与制动，完成车位停靠；到位后施加驻车制动。
相关方交互
乘客离开车辆后由系统自主完成泊车；平台向运营端上报泊车结果。
预期结果
车辆准确、平稳泊入车位并进入驻车模式。
异常分支
车位环境变化或低速避障需求出现时，平台重新规划并制动避让。

场景 O-4 单点失效降级与最小风险处置

FAULT MANAGEMENT · REDUNDANCY
前置条件
运行中某传感器、执行器、电源或通信链路被诊断为故障。
系统行为
冗余单元接管，先进入降级模式限制车速与功能；若故障达到关键等级，进入 MRC：自主靠边减速停车、开启警示。
相关方交互
平台分级告警并上报运营端；远程安全员获知状态，判断是否介入；维保团队后续回场检修。
预期结果
单点失效不导致失控，车辆进入可控、可识别的安全状态。
异常分支
冗余链路同时异常时，以最大制动能力在安全区域停车，并保留完整故障日志。

场景 O-5 回场检修与部件更换

MAINTENANCE · SUPPORT
前置条件
车辆回场，维保人员接入诊断工具，读取故障码与运行日志。
系统行为
平台提供各子系统状态与故障定位，支持部件更换后的自检与标定校验。
相关方交互
维保团队按标准流程检修；供应商配合备件与技术支持；研发团队依据数据复盘。
预期结果
故障排除，自检通过，车辆重新具备上线运营条件。
异常分支
若备件或标定未达标，车辆保持禁用状态，不得投入运营。

6.3 – 6.6其他生存周期概念

6.3 采办概念

平台与子系统按车规零部件流程采购或联合开发；供方依据冻结的接口与规格交付，关键件保留双供应或冗余备份。

6.4 部署概念

随整车集成下线，完成安装检查、标定校验与整车自检后投放；部署记录与车辆配置一一对应。

6.5 支持概念

运营期提供远程监控、在线诊断、保养提醒、备件供应与现场维修支持，软件缺陷通过 OTA 修复。

6.6 弃置概念

车辆退役时，对高压部件、电控单元与传感器进行拆解回收，清除车载数据与标定信息，记录弃置过程。
